On and X is where I want to pop the hood today, because portability lives in a single
graph file rather than a training framework runtime.
Think of an on and X model as a directed graph.
Operators like Con, Matt Mall, and Relu sit on the nodes, and tensors with a shape and an element type travel the edges.
Constant tensors in that same graph hold the weights and initializers, which means one file carries the whole executable description.
Run times can load that identical graph on CPU, GPU, or specialized accelerators without rebuilding the original training frameworks execution engine.
The specification is proto-buff-based, a structured binary format, so any compliant parser can validate
shapes and types before execution, and catch mismatches that would otherwise surface only
at inference time.
Dynamic control flow has to be expressed through control flow operators rather than Python
level branching, which limits some research models until they are rewritten.
The format originated as Toffee inside the PyTorch team at Facebook before being renamed
and announced jointly with Microsoft in 2017,
and it later became a Linux Foundation AI graduate project.
When the target hardware supports a matching kernel
for every operator in the graph,
teams see the largest gains,
otherwise they fall back to less efficient generic implementations.
The IR specification document defines normative semantics
while the protofiles supply the concrete syntax,
and a C++ validator with a Python wrapper
helps catch violations early.
Use ONX when you need to move a train model between frameworks or deploy it on hardware
that lacks a native pie torch or TensorFlow runtime.
Stay with the original framework when rapid iteration on custom operators matters more
than portability.
