### Model Updates
**HappyHorse 1.1: Alibaba Cloud**
Alibaba released HappyHorse 1.1, a 15-billion-parameter unified self-attention Transformer that handles text, image, video, and audio in one pass. The model now supports multi-image reference-to-video (R2V) for consistent character identity across shots, strengthened motion modeling, and zero-drift lip sync for up to 15 seconds of 1080p output. It sits at #2 on the Artificial Analysis Video Arena leaderboards, ahead of Google Veo-3.1 in both text-to-video and image-to-video. The upgrade ships with full API access on Alibaba Cloud Model Studio and a 40% launch discount for the first two weeks. Builders working on advertising or serialized content should test the R2V reference workflow this week to see whether identity consistency removes the need for traditional post-production fixes. Source: [venturebeat.com](https://venturebeat.com/technology/alibabas-ai-video-model-rises-to-no-2-in-global-rankings-as-openais-sora-and-bytedances-seedance-fall-away)

**Fugu and Fugu Ultra: Sakana AI**
Sakana launched Fugu, a multi-agent orchestration system that routes queries across a swappable pool of models and exposes a single OpenAI-compatible API. Fugu Ultra uses fixed pricing at $5 per million input tokens and $30 per million output tokens, while the standard tier charges the highest underlying model rate. On LiveCodeBench it scores 92.9–93.2, beating Claude Fable 5’s 89.8; on GPQA-Diamond it reaches 95.5. The system is closed-source and restricted from the EU/EEA during GDPR alignment work. Developers facing vendor lock-in or sudden model access changes should try routing a complex multi-step coding task through Fugu Ultra this week to compare orchestration overhead against direct frontier calls. Source: [venturebeat.com](https://venturebeat.com/orchestration/no-claude-fable-5-no-problem-sakana-achieves-frontier-performance-with-new-fugu-multi-model-auto-synthesis-system)

**Self-Harness framework: Shanghai Artificial Intelligence Laboratory**
Researchers released Self-Harness, a three-stage loop that lets an agent mine its own failure traces, propose minimal harness edits, and validate them through regression testing. On Terminal-Bench-2.0 the system delivered 33–60% relative gains across MiniMax M2.5, Qwen3.5-35B-A3B, and GLM-5 without changing the underlying model or tools. The method requires deterministic verifiers and is best suited to measurable environments such as coding or DevOps pipelines. Teams maintaining custom agents should review the paper to see whether adding a weakness-mining step to their evaluation harness reduces manual prompt tuning. Source: [venturebeat.com](https://venturebeat.com/orchestration/researchers-introduce-self-harness-a-framework-that-lets-ai-agents-rewrite-their-own-rules-boosting-performance-up-to-60)

### Practical & Community
**Moebius 0.2B browser demo: Simon Willison**
Simon Willison ported the 0.2B Moebius image inpainting model to ONNX and WebGPU so it runs entirely in the browser after a ~1.3 GB download. The demo at simonw.github.io/moebius-web/ lets users open any image, mark regions, and run inpainting with caching via the CacheStorage API. The project was built with Claude Code and publishes converted weights to Hugging Face. Anyone experimenting with client-side vision tools should open the demo in Chrome or Firefox and test inpainting on their own photos to judge whether the 1.3 GB first-load cost is acceptable for their use case. Source: [x.com](https://x.com/simonw/status/2069213084305301903)

### Under the Hood: ONNX Export and WebGPU Execution for Client-Side Models
Everyone talks about running models in the browser as if it is simply a matter of loading weights. In practice, the pipeline requires exporting a PyTorch graph to ONNX with a specific opset (here opset 18), converting every operator into a portable computation graph, then mapping that graph onto WebGPU shaders through ONNX Runtime Web. The export step records dynamic axes so batch and spatial dimensions remain flexible, but it also forces the model to drop any PyTorch-specific control flow that cannot be expressed in the ONNX operator set. Once converted, the 1.24 GB of weights must be fetched and cached; the CacheStorage API keeps the tensors resident across reloads, cutting subsequent loads from minutes to seconds. The quality trade-off is real: operators that lack direct WebGPU equivalents are emulated, adding measurable latency on every forward pass. When the model stays under roughly 1.5 GB and the workload is embarrassingly parallel (single-image inpainting, short audio clips), the approach wins on privacy and zero-install deployment. The moment you need custom CUDA kernels or multi-gigabyte context, the same model still belongs on a server with a proper GPU runtime.
