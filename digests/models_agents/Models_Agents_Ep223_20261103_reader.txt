Static batches stall a GPU until the slowest sequence finishes, so pop the hood on continuous batching: new requests join an in-flight batch as soon as earlier sequences finish.

The key engineering move is dynamic key-value cache management, where each request keeps its own key-value cache slice that can be appended to on the fly while the attention mask is recomputed for the current active set.

That removes the classic constraint that all requests must finish together and replaces it with a scheduler that decides, at every step, which sequences to run and which to pause.

The throughput gain is largest when request lengths vary widely.

A fleet seeing a mix of short chat turns and long document summaries can reach two to four times higher tokens per second than static batching at the same model size.

The tradeoff is added scheduling overhead and more complex memory fragmentation, because the key-value cache is no longer a single contiguous block.

Most production servers therefore combine continuous batching with paged attention or block-wise cache allocation to keep fragmentation under control.

Use continuous batching when average request length is short relative to the model context and arrival rate is high, and fall back to static or semi-static batching when requests are uniformly long or when strict per-request latency service-level agreements dominate.

Cache-eviction policies must be tuned per workload; an aggressive eviction rule that works for chat can silently drop long-context retrieval sessions.
